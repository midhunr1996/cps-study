## 1. System Design = two halves

🧒 **Story:** Before you touch a screwdriver, Cy the owl splits the word for you. **System Design = "the System" (its purpose) + "the Design" (how you build it).** Robi's *purpose* is "clean the floor"; the *design* is the wiring diagram and code that make it happen.

📝 **Write in exam:**
- **System Design consists of two parts: the System (purpose) and the Design (how).**

🧠 **Hook:** *System = WHAT. Design = HOW.* Two words, two halves of the whole course.

## 2. What *is* a system?

🧒 **Story:** Cy hoots: *"What is a system?"* Look at Robi: lots of **different parts** all chasing **one purpose**, and you can draw a **fence** around it separating it from the world. If the parts were all the same and had no shared purpose, it'd just be a **pile** (accumulation), not a system.

📝 **Write in exam — definition:**
- **A system = a group of associated components that work together for the same purpose and that can be bordered from the environment.**
- Components have **different characteristics** — otherwise it's an **accumulation**, not a system.
- Systems are **clearly bordered** from others/environment; sometimes **partial overlaps at interfaces**.

🧠 **Hook:** *Different parts · one purpose · a fence around it.* No fence or all-same-parts = not a system.

**Examples (one weird image each):**
- 🌌🍃🫁 **Natural** (grew with NO human): **Galaxy** (life), **Leaf** (photosynthesis), **Lung** (breathing).
- 🎹✈️🤖 **Artificial** (built by people): **Piano** (sound), **Airplane** (fly), **Robot** (human expressions). Also **search engine, sports team, organization**.

## 3. System Classification

🧒 **Story:** Cy shows a **coral-reef tank** — living coral + machine pumps = a mix. Systems sort into **3 bins**, and man-made ones into **3 more**, and we also tag each by **how open its doors are**.

📝 **Write in exam:**
- **Types of systems:** Natural · Artificial · **Biotechnical**.
- **Types of man-made systems:** **Technical** (machines, tools) · **Social** (family, groups, work) · **Sociotechnical** (technical + social influencing each other, e.g. information system, work system).
- **By exchange with environment:** **Open** (full interfaces — info/material/energy) · **Partly open** (small pre-defined data, e.g. **OBD** in a car) · **Isolated** (nothing exchanged).
- Parts can differ: a robot's **tracking system = isolated**, but its **map → open Bluetooth**.

🧠 **Hook:** **3 doors on Robi** → wide-Open · mail-slot (Partly, "OBD") · welded-shut (Isolated). Classes: *Nature, Machines, Society — and the reef mixes them (biotechnical/sociotechnical).*

## 4. Cyber, Cybernetics & CPS

🧒 **Story:** Why the "Cyber" in Cyber-Physical? **Cyber = short for cybernetics = controlling machines using feedback** — like Robi's brain constantly asking *"am I where I should be?"* and correcting. The owl draws Robi's **control loop**: Target − Current = a gap → Controller → Actuator → the world reacts → Sensor reads it → loop again.

📝 **Write in exam — cybernetics:**
- **Cyber = short form of cybernetics.**
- **Cybernetics = control of machines** including the **feedback of sense organs** (analogy to lifeforms) and the **feedback of social interactions** (communication).

📝 **Cybernetic control loop (in order):** **Target value → difference (target − current) → Controller → Command → Actuator → Action → System/Environment → Reaction → Sensor → Current value → fed back (−).**

📝 **"Cyber" umbrella term:** prefix for computer/virtual-reality topics — **Cybersecurity, Cyberspace, Cyberwarfare, Cybercrime, Cyber-attack, Cyborgs** (organic + biomechatronic crossover).

🧠 **Hook:** *Cyber = feedback brain.* The loop is a circle: **gap → fix → measure → repeat.**

### 4a. Mechatronic vs CPS (favourite exam contrast)
🧒 **Story:** A **lone washing machine** is **mechatronic** — software + hardware, sealed, standalone. Now let the washer **text the solar panels** to run when the sun shines — that networked smart-home is a **CPS**.

📝 **Write in exam:**
- **Mechatronic system = software + hardware (mechanics & electronics); can be standalone/closed.** E.g. washing machine.
- **CPS = intercommunicating software (especially embedded, via internet = "cyber") + hardware (= "physical"); for large-scale, distributed networks (IoT).** E.g. home automation linking washer + photovoltaic.
- **No sharp deviation** between mechatronic and CPS.
- **Applied to this lecture**, a system = **physical** (Sensors, Actuators, PCB & wires) + **cyber** (Processing unit, AI, general software) → a CPS.

🧠 **Hook:** *Mechatronic = lonely washer. CPS = washer that texts the solar panels.*

Spokes are **extra properties** (safety, EMC, thermal…). The **rim is painted in 3 colours** = the three building trades: **mechanics, E/E, software**. - Customer raises requirements **on system level**.

🧠 **Hook:** **Wheel = Hub (DNA) · Spokes (properties) · 3-colour Rim (mech/E-E/SW) · Customer at the edge.**

## 6. System Structure (SIPOC)

🧒 **Story:** Every system, says Cy, is secretly a **conveyor belt**: something comes **in**, gets **processed**, goes **out**. That's **SIPOC** (Supplier-Input-Process-Output-Customer). For Robi: a **Sensor** feels → a **wire** carries → the **Brain/Logic** decides → a **wire** carries → a **Motor** acts.

📝 **Write in exam:**
- Every process = **SIPOC** (Supplier · Input · Process · Output · Customer).
- High-level system structure: **Sensor → Connector → Logic → Connector → Actuator/Visualizer.**
  - **Connector** = PCB, wire, wireless, …
  - **Logic** = software, IC, calculator, state machine, AI, …
  - **Actuator/Visualizer** = motor, valve, HMI, database, …
- **ChatGPT example:** prompt page (sensor) → to server (connector) → AI magic (logic) → to browser (connector) → output field (visualizer).
- **Sorting-machine example:** colour sensor 0–5 V → wire to TXT controller → threshold picks pusher 1/2/3 → wire to motor driver → pusher fires.

🧠 **Hook:** **"See It Process Output Customer"** = **S**ensor → **C**onnector → **L**ogic → **C**onnector → **A**ctuator. Conveyor belt, always.

## 7. System Levels & Tiers

🧒 **Story:** Pull Robi apart like **Russian nesting dolls**: the big **Supersystem** holds **Systems**, which hold **Sub-systems**, which hold **Components**. A higher level is just the **sum** of the dolls inside it.

📝 **Write in exam:**
- Levels (top→bottom): **Supersystem (4, rare) → System (3) → Sub-system (2) → Component (1).**
- A higher level = the **sum of the elements below**.
- Lower-level count is **variable but always > 1** (else the level wouldn't exist).
- **Supersystem & Sub-system are optional; System & Component always exist.**
- **Same element, different level** depending on viewpoint: for a **car-maker**, the car = system, motor = subsystem, winding = component; for a **screw supplier**, the **screw** = system, its head/thread = subsystem.
- In industry, supplier levels are called **"tiers"** (manufacturer → tier-1 → tier-2 → tier-3 → …).

🧠 **Hook:** **Nesting dolls.** *System + Component are the two dolls that MUST exist; Super/Sub are optional. Your level depends on who's holding the doll (tier).*

## 8. Components

🧒 **Story:** Tip Robi out onto the bench — a **pile of bricks**. Some you can touch (**hardware, software, liquids**), some you can't (**talents, roles, ideas**). Each brick is **fenced off** and does its **own job**.

📝 **Write in exam:**
- **Components = the basic elements of a system.**
- **Real (material):** Hardware (electronics, mechanics, hydraulics) · Software (functions, interfaces) · Material/consumables (chemicals, liquids).
- **Immaterial:** Talents & Roles · Ideas.
- Components are **clearly bordered** and have **different functions/tasks**.

🧠 **Hook:** *Brick pile — touchable bricks (HW/SW/liquids) + invisible bricks (people/ideas).*

## 9. Emergence

🧒 **Story:** Drop **one** sulphur crumb — colourless. Pour a **pile** — it glows **yellow**. The colour belongs to the *group*, not the crumb. That surprise extra property = **emergence**, "1+1=3". (One molecule has no pressure; a gas does.) But careful: if something only *seems* magic because **we're ignorant**, that's **not** emergence — it vanishes once science catches up.

📝 **Write in exam:**
- **Emergence = a system has other properties than the simple sum of its components ("1+1=3").**
- Examples: **single sulphur atom = no colour, many = yellow**; **single molecule = no pressure, gas = pressure**.
- **Ignorance is NOT emergence** — sometimes effects are just **unknown** due to low state-of-the-art knowledge and **disappear** as knowledge evolves.

🧠 **Hook:** *Glowing sulphur pile.* The property lives in the crowd, not the crumb. *Don't-know ≠ emergence.*

## 10. Complexity & VUCA

🧒 **Story:** A **storm cloud** rolls over the workshop — the modern world is **VUCA**: a *Very Ugly Chaotic Atmosphere*. Then Cy plays a game: a **subway map** vs the **weather** — which is *complex*? The map is only **complicated** (hard but all rules known); the weather is truly **complex** (rules unknown, all tangled).

📝 **VUCA:** **V**olatile (discontinuity, high speed, big swings) · **U**ncertain (unclear outcomes, low predictability, things "emerge from nothing") · **C**omplex (many layers, fuzzy boundaries) · **A**mbiguous (no simple description, multiple interpretations).

📝 **What makes a system complex:** order of components follows **technical/natural-science principles** → a **predictable pattern**; the **amount, order & interaction** of components set the **complexity level**; **complex systems can't be broken into easy problems.**

📝 **Properties of complex systems:** **Agent-based · Non-linear** (small change → totally different result) **· Emergence · Open · Self-organised** (no overarching controller) **· Self-regulating · Path-dependencies** (history matters, not just current state).

📝 **COMPLICATED vs COMPLEX (key table):**

| Complicated | Complex |
|---|---|
| All elements known | Not all known |
| Clear rules & dependencies | (Partly) unknown |
| Much effort but **predictable** | **No prediction** |
| Removable by training/knowledge | **Cannot** be removed |
| PM tool → **waterfall** | PM tool → **agile (SCRUM)** |

Examples: **subway map = complicated**; **weather = complex**.

📝 **Special kinds:**
- **CAS (Complex Adaptive System):** changes itself (adapt/learn), not static — **stock exchange, human brain.**
- **MAS / ABM (Multi-Agent System):** many homogeneous/heterogeneous **agents** communicate; autonomous, distributed, self-organised, **no boss**; an agent **broadcasts** when it takes a job to avoid double work — **ant colony, DAI.**
- **Measuring complexity (IT):** "Computational Complexity Theory" via **resource demand** — computing time, storage, chip size, number of parallel chips.

🧠 **Hook:** **VUCA = the storm.** *Complicated = subway map (waterfall). Complex = weather (SCRUM).* Complex props: *agents in a non-linear, open, self-run system that remembers its past.*

## 11. Degree of Connectivity

🧒 **Story:** Tie Robi's parts together with **string** until they form a **spider web**. The *more knots and threads*, the higher the **connectivity**. Rule: parts in the **same unit** may talk; parts in **different units on the same level must NOT** — if they do, you **drew the border wrong** (→ wrong responsibilities!).

📝 **Write in exam:**
- Same-level, **same-unit** elements **may** interact & affect each other.
- **No** interaction between same-level elements in **different units** — else the **border is wrong → risk of wrong responsibilities.**
- Interactions swap **information / material / energy**, are **interdependent**, **not unidirectional**.
- **Degree of connectivity** = (amount of different **nodes**) + (amount of causal **connections**).
- Measured by the **clustering coefficient** (compute it **exactly, no rounding**; a **bidirectional** link counts as **2**).

🧠 **Hook:** **Spider web** — count knots + threads; a two-way thread = **2**. Cross-unit threads = a *wiring mistake*.

## 12. System Dynamics & Chaos Theory

🧒 **Story:** You can't sketch Robi's full behaviour on a napkin — too tangled. So you **simulate** the whole system on a computer and run it **1000 times**. That's **System Dynamics**. Then a **butterfly** flaps, the simulation goes wild and unpredictable — **Chaos Theory**.

📝 **System Dynamics:** complex systems **can't be described easily/linearly** → **model & simulate the whole system**. Two variants:
- **Qualitative** — find **feedback loops** (how items impact each other): **reinforcing loops** = positive coupling, **balancing loops** = negative coupling; **easier** than quantitative; good **overview**.
- **Quantitative** — model & simulate the whole system; results are **real numbers**; **many scenarios/runs**; uses **flow charts & process views**; finds **non-linear effects**.

📝 **Chaos Theory:** field studying **non-linear dynamic systems**; the **"butterfly effect"** — small changes → big effect, **prediction impossible**. Examples: **turbulent gas flow, internet.**

🧠 **Hook:** *Simulate 1000 times = System Dynamics (Qualitative = arrows/loops, Quantitative = numbers). Butterfly = Chaos.*

## 13. Design

🧒 **Story:** Now an **artist with a paintbrush** turns Robi's requirements into something real — drawings, models, code. But the artist can't ignore the **factory**: design, integration and production all **pull on each other**. A design nobody can manufacture (a ball inside a ball, or all-gold wires) is useless.

📝 **Write in exam:**
- **Design = the process of translating requirements (respecting the system purpose) into a (technical) solution.**
- **Deliverables:** Plan · Drawings/schematics · Models · Software code · …
- **Design, integration & production can't be strictly divided** — they influence each other.
- Build **prototypes** upfront and **test** them.
- Without knowing **production capabilities** → risk of a **non-producible** (ball-in-ball) or **non-commercially-producible** (all-gold wires) part.

🧠 **Hook:** *Paintbrush turns requirements → drawings/models/code; but the factory is always watching.*

## 14. System Design Process

🧒 **Story:** Zoom out to the whole **company factory**. Every process is one of **3 lanes**: the **core** lane (where money is made with customers/suppliers), the **management** lane (steering), and the **support** lane (helpers). BMW's core lane reads like a relay: **Idea → Offer → Order → Delivery → Customer-Care.**

📝 **Write in exam:**
- **3 process classes:** **Core** (business with customers & suppliers; **value-adding**) · **Management** · **Support**. Flow: **customer requirement → core process → customer satisfaction.**
- **BMW core process (simplified):** **ItO** (Idea→Offer) · **OtO** (Offer→Order) · **OtD** (Order→Delivery) · **DtCC** (Delivery→Customer-Care).
- **ItO** = development from requirement → ideas/concepts → implementation; purchasing procures materials/tools; after **test & validation (verification)** and **industrialisation** → release for production. Aim: **meet all requirements, build the optimal product.**
- **System design** = the part of the core process turning requirements into the technical solution (ItO).

🧠 **Hook:** **3 lanes = Core · Management · Support.** BMW relay: **I-O-O-D** → *Idea, Offer, Order, Delivery (then Care).*

## 15. System Engineering — the 7 steps

🧒 **Story:** Here's the **big gear-loop** that actually builds Robi. Five steps run in order — **Requirements → Ideation → Design → Test → Release** — and two more, **Risk** ☢️ and **Change** 🔁, **hug the whole loop** the entire time. It's defined by a standard, **ISO 15288**.

📝 **Write in exam — System Engineering is:**
- an **interdisciplinary** field of classical engineering + engineering management;
- **design, integrate & manage complex systems over their life cycle**;
- defined in **ISO/IEC 15288**.

📝 **The steps (in order):**
1. **Requirement Management** — analyse the problem & requests (**Customer, Law, LeLe**); break into requirements; define system requirements.
2. **Ideation / Concept** — creative search for ideas/solutions (maybe **research**!); define functions; create **system architecture**; break (super)system → subsystem → component; break requirements into levels; **interface design**.
3. **Design / Realization** — model, simulate, analyse; implement into real **HW/E-E/SW**; integrate levels; document. → **core engineering work.**
4. **Test & Verification & Validation** — test design, the **"test of the test"**, planning, execution (virtual + HW). → **proof by measurement** every requirement is met.
5. **Release** — sign off; release to production; take over **accountability** to the customer.
- **Risk Management** (surrounding) — check risks to product/time/cost/safety (e.g. **FMEA**); deviation management.
- **Change Management** (surrounding) — update system on changing requirements (**new law, customer change of mind, LeLe/field issues**); **version control**.

🧒 **Why it matters:** without system design & requirement management you get the famous **"tree-swing" cartoon** — every department builds something different from what the customer wanted.

🧠 **Hook:** **Gear-loop: R-I-D-T-R** (Requirements, Ideation, Design, Test, Release) wrapped by **Risk ☢️ + Change 🔁.** Standard = **15288.**

## 16. System Engineering — Challenges

🧒 **Story:** A **runner at the start line** is sweating because modern CPS projects are brutal: the world went global, everything connects to everything, customers want endless variants, and you can't even prove the thing is safe.

📝 **Write in exam — challenges:**
- **Globalization** → more complex projects; **many suppliers**; rising **legal** specs; **unclear responsibilities** (fuzzy boundaries).
- **Interdisciplinary** approach mandatory (communication across specialists).
- **Diversity of interfaces** → must have **consistent control of all interfaces**.
- **Complexity of requirements** → more **dynamics** in requirement management.
- **More product variants** → costly change/variant management → **component kits (reusable units)**. *(Fun fact: a VW Golf has ~425 billion wiring-harness combinations.)*
- **Reduced cycle time** → hard **quality–cost–time trade-off** (see VUCA).
- **Distributed sensor network** → **sensor fusion** of data spread by location (camera + lidar).
- **Handling communication** → systems must intercommunicate (when? which path — internet/Bluetooth?).
- **Information gathering** → lots of data, ever-changing, not all accessible.
- **Hard to verify** → can't stop the system, who's the root cause, hard to debug, AI keeps changing.
- **Safety** → is network data trustworthy? new attack points; can't control the whole network.

🧒 **Accountability twist:** an autonomous AI car crashes — **who's to blame?** Owner, customer, "driver" friend, sensor supplier, sensor-fusion dev, car maker, SW/HW devs, AI dev, AI trainer, dataset supplier, internet/interconnection suppliers… → **the point is the future challenge of mastering this complexity.**

🧠 **Hook:** **Sweating runner.** Theme word: *everything got bigger, more connected, more varied, harder to verify & secure.* "Who crashed the robot-car?" = nobody can tell.

## 17. MBSE, MDSD & Digital Engineering

🧒 **Story:** Finally, three power-tools. **MBSE** = the System Wheel **with a working model** so every discipline reads the same picture. **MDSD** = a **vending machine** that spits out finished code/tests/docs straight from a diagram (Simulink → C). **Digital Engineering** = a **ghost-twin** of Robi you can watch and poke live.

📝 **MBSE (Model-Based Systems Engineering):** System Wheel **+ a model**; not only text — **model the system**; cross-discipline communication; holds **all** system info **independent of realization domains**; needs a **harmonized modelling language** (software-supported); successor = **Digital Engineering**.
- **Benefits:** better visualization · architectures & dependencies → **traceability** · automated tests/plausibility · **different views** of one system · documented interconnections → foresee change impact · **direct code generation** (MDSD).
- **Languages: UML** & **SysML.**

📝 **MDSD / MDD (Model-Driven Software Development):** auto-generate **functional software, tests, documentation** from the model **without coding** (e.g. **Simulink → C-code**).
- **Advantages:** higher **abstraction** (clearer) · faster development · faster **system-fitting test cases.**
- **Disadvantages:** more **initial modelling effort** · not all functions auto-generate → **manual code** integration tricky · **troubleshooting** harder due to manual code.

📝 **Digital Engineering:** defined by **INCOSE** (and **GfSE** in Germany); uses **"digital twins"** to see performance **live** and **interact virtually**; uses **MBSE · AI · CAD/CAE · additive manufacturing · VR/AR.**

🧠 **Hook:** **MBSE = model everyone shares. MDSD = vending machine (diagram → code). Digital Engineering = ghost-twin.** Languages = **UML/SysML**; councils = **INCOSE/GfSE**.
