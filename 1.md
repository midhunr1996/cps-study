## System Design — the two halves

**System Design consists of two parts:**
- **The System** — the *purpose* (what it is / what it should do).
- **The Design** — the *how* (how the purpose is realised).

---

## What is a System?

> **A system = a group of associated components that work together for the same purpose and that can be bordered from the environment.**

- The components have **different characteristics and features** — otherwise it would be a mere **accumulation**, not a system.
- Systems are **clearly bordered** from other systems and the environment. Sometimes there are **partial overlaps at interfaces**.

### Examples of systems

**Natural systems** are "developed" *without active human input*:
- **Galaxy** — linking of planets, gas and dust enabling life.
- **Leaf** — combination of channels, cells and chemicals enabling photosynthesis.
- **Lung** — combination of muscles, meshes and tubes enabling breathing.

**Artificial systems** are *made by mankind*:
- **Piano** — keys, strings, hammers… to create a sound.
- **Airplane** — wings and jet engines to be able to fly.
- **Robot** — motors, wires and AI to simulate human expressions.
- **Search engine** — software functions + HMI to find data within large sets.
- **Sports team** — different roles (e.g. goalkeeper) forming a successful team.
- **Organization** — different talents and jobs building a successful company.

## System Classification

### Types of systems
- **Natural systems**
- **Artificial systems** (man-made)
- **Biotechnical systems**

### Types of man-made (artificial) systems
- **Technical systems** — e.g. machines, tools, …
- **Social systems** — e.g. family, ethnos, social groups, work, …
- **Sociotechnical systems** — combine technical and social aspects that influence each other, e.g. information system, work system, …

### Classification by exchange with the environment
- **Open** — system has interfaces to its environment, exchanging information, material, energy, …
- **Partly open** — exchanges a pre-defined (small) amount of data, e.g. **OBD** for a car.
- **Isolated** — nothing is exchanged with the environment.

> Parts of the system can be classified differently. E.g. the **tracking system** of a cleaning robot is *isolated*, while its **recorded map** can be visualised via the robot's *open* Bluetooth interface.

## Cyber, Cybernetics & CPS

### Definition of "Cyber"
- **Cyber** = short form of **cybernetics**.
- **Cybernetics** = **control of machines** including:
  - the **feedback of sense organs** (analogy to lifeforms), and
  - the **feedback of social interactions** (communication).

### Structure of a cybernetic system (control loop)
A closed feedback control loop:

`Target value → (compare: difference = target − current) → Controller → Command → Actuator → Action → System / Environment → Reaction → Sensor → Current value → (fed back, subtracted from target)`

- The **difference** (Target − Current) drives the **Controller**, which issues a **Command** to the **Actuator**.
- The actuator's **Action** changes the **System/Environment**, whose **Reaction** is measured by the **Sensor**, producing the **Current value** that is fed back (negative feedback) to the comparison point.

### "Cyber" as an umbrella term
Mainly used as a **prefix** for topics associated with computer applications focusing on virtual reality, e.g.:
- Cybersecurity · Cyberspace · Cyberwarfare · Cybercrime · Cyber-attack
- **Cyborgs** — organic ("man") and biomechatronic ("machine") crossover.

### Mechatronic system vs Cyber-Physical System (CPS)

| | **Mechatronic system** | **Cyber-Physical System (CPS)** |
|---|---|---|
| **Definition** | Merge of **software** + **hardware** (mechanics & electronics) | Merge of **software components that intercommunicate** (e.g. via the internet — *cyber*) + **hardware** (mechanics & electronics — *physical*) |
| **Scope** | Can be a **standalone, closed** system | More applicable to **large-scale, distributed networks** (**IoT** — Internet of Things) |
| **Example** | Washing machine | **Home automation** controlling energy consumption by connecting the washing machine with the photovoltaic system, … |

> There is **no sharp distinction** between mechatronic systems and CPS.

### "Things" of a system (applied to this lecture)
Applied to this lecture, a system is a combination of:
- **Physical:** Sensors · Actuators · PCB & wires
- **Cyber:** Processing unit · AI · General software

→ together forming a **Cyber-Physical System (CPS)**.

## System Wheel

The **System Wheel** is the model used throughout the course (more detail comes in *Requirement Management*). It has concentric rings, viewed from the inside out:

- **Core system properties — the "DNA" (data sheet):** the inner ring; what would be written on a one-page datasheet. Example properties: **performance, consumption, acoustic, costs, reliability, weight, size**.
- **Extended system properties (the "Wirkketten" / effect chains):** e.g. **acoustical behaviour, performance & efficiency, data acquisition/access & security, design for production/service & upgrade capability, safety, EMC, sustainability, reliability, thermal behaviour, volumetric behaviour & design**.
- **Realization domain:** the three engineering disciplines that build it — **mechanics**, **E/E** (electrics/electronics), and **software** (each roughly ⅓ of a modern product).
- **Customer** sits at the outer edge, raising requirements on the system.

> Details for each section are covered later in **Requirement Management**.

## System Structure (SIPOC)

In general, every process can be described via the **SIPOC** logic (Supplier · Input · Process · Output · Customer).

Transferred into the **high-level structure of a system**, every system has this chain:

`Sensor → Connector → Logic → Connector → Actuator / Visualizer`

| Block | What it is | Examples |
|---|---|---|
| **Sensor** | input element | measures a physical quantity |
| **Connector** | links blocks | PCB, wire, wireless, … |
| **Logic** | processing | software, IC, calculator, state machine, AI, … |
| **Connector** | links blocks | PCB, wire, wireless, … |
| **Actuator / Visualizer** | output element | motor, valve, HMI, database, … |

### Example — ChatGPT
- **Sensor:** prompt webpage
- **Connector:** data transfer to server
- **Logic:** "magic of AI"
- **Connector:** data transfer to browser
- **Actuator/Visualizer:** visualise data in the output field

### Example — Sorting machine (fischertechnik)
- **Sensor:** sensor measuring colour, output 0…5 V
- **Connector:** wire to the TXT controller
- **Logic:** based on a threshold, activate pusher 1, 2 or 3
- **Connector:** wire to motor driver
- **Actuator/Visualizer:** driver activates the pusher

## System Levels & Tiers

A system can be divided into **levels / tiers**. A **higher level is the sum of the elements below it**.

| Level | Name | Notes |
|:---:|---|---|
| 4 | **Supersystem** | optional; used rarely |
| 3 | **System** | always exists |
| 2 | **Sub-system** | optional |
| 1 | **Component** | always exists; the basic element |

- The number of elements on a lower level is **variable but always greater than 1** — otherwise the lower level would equal the higher one, and that level would not exist.
- **Supersystem and subsystem are optional**, but **System and Components always exist**.

### Same element, different level (depends on point of view)
The very same element can be a different level depending on integration / viewpoint:

| Level | Car manufacturer | Tier-1 screw supplier |
|---|---|---|
| **Super-system** | — | car |
| **System** | car | screw |
| **Sub-system** | electrical motor, wheels | screw-head, thread |
| **Component** | winding, housing / tyre, rim | grease, coating / core, coating |

### Tiers in industry
In industry, the supplier levels are called **"tiers"**: a **manufacturer** sources from **tier-1** suppliers, who source from **tier-2**, who source from **tier-3**, … down to the **customer** chain of suppliers.

**Real (material):**

**Immaterial:**
- **Talents & Roles**
- **Ideas**

- Components are **clearly bordered** from each other.
- Components have **different functions and tasks**.

## Emergence

> **Emergence = a system can have other properties than the simple sum of the properties of its single components.** ("1 + 1 = 3".)

**Examples:**
- A **single sulphur atom has no colour** — several sulphur atoms together are **yellow**.
- A **single molecule has no pressure** — many molecules combined into a **gas** create the new property **"pressure"**.

**Don't mismatch — ignorance is NOT emergence:**
- Sometimes phenomena are caused by the current "too low" **state-of-the-art knowledge**.
- Relevant effects are simply **unknown**.
- With evolving technical knowledge, they **disappear**.
- This **ignorance is not emergence**.

## Complexity & VUCA

### VUCA
| Letter | Term | Meaning |
|:---:|---|---|
| **V** | volatile | discontinuity; high speed & intensity; large ranges of fluctuation |
| **U** | uncertain | countless scenarios with unclear outcome; unknown future / low predictability; new things seem to emerge out of "nothing" |
| **C** | complex | elements connected in many layers; many different systems; clear system boundaries are difficult to define |
| **A** | ambiguous | no more simple description; situations can be interpreted differently |

### What makes a system complex
- The **order** of components within a system is based on **technical and natural-science principles**.
- This arrangement causes a **predictable pattern** of how the system reacts.
- The **amount of different components, their order and interaction** define the **level of complexity**.
- **Complex systems cannot be broken down** into easier-to-handle problems.

### Properties of complex systems
*(Not all must apply, but in general most do.)*
- **Agent-based** — single units that interact with each other.
- **Non-linear** — small changes result in a completely different result.
- **Emergence** — system has other properties than its units.
- **Open** — interaction with the environment (not closed).
- **Self-organised** — no single overarching controller.
- **Self-regulating** — achieves balance without an overarching controller.
- **Path dependencies** — behaviour depends not only on the current state but also on the **history** (what came before).

### Complicated vs Complex (key exam table)

| **COMPLICATED** | **COMPLEX** |
|---|---|
| All elements known | Not all elements known |
| Clear rules (cause & effect) | Rules (partly) unknown |
| Clear dependencies | Dependencies (partly) unknown |
| Much effort but **predictable** | **Prediction not possible** |
| Can be "removed" by training & knowledge | **Cannot** be removed |
| PM tool → **waterfall model** | PM tool → **agile (SCRUM)** |

**Survey examples:**
- **Subway grid plan (Munich)** → **complicated** — many stations/lines, but all follow clear rules and dependencies; all elements known; much effort but predictable ("get in here → after 5 stations you end up there").
- **Weather** → **complex** — not all elements known, all interconnected, and the kind of interconnection is also not known.

### Special kinds of complex systems
- **Complex Adaptive Systems (CAS)** — systems that **change themselves** (adapt/learn) based on their environment, so they are **not statically analysable**. Examples: **stock exchange, human brain**.
- **Multi-Agent System (MAS) / Agent-Based Modelling (ABM):**
  - Several **homogeneous or heterogeneous units** ("agents") that **communicate** with each other.
  - **Autonomous and distributed** systems that harmonise knowledge, targets and skills to act coordinated / resolve issues.
  - Agents solve a big problem a single agent couldn't, **without an overarching controller** (self-organised). If an agent takes over a topic, it **broadcasts** this to avoid double work.
  - Examples: **algorithms of an ant colony**, **DAI** (distributed artificial intelligence).

### Measurement of complexity
For IT, complexity can be measured by **"Computational Complexity Theory"** via **resource demand**:
- Computational time
- Storage demand
- Needed chip size
- Amount of parallel computing chips needed

## Degree of Connectivity

- Elements **on the same level and within the same unit** can interact with and affect each other (but don't have to).
- There must be **no interaction between elements on the same level but in different units** — if there is, the **definition/border of the element is set wrong** → **risk of wrong responsibilities!**
- The interaction can swap **information, material, energy**; it is **interdependent and normally not unidirectional**.
- Depending on the number of connections, a **degree of connectivity** results.

The degree of connectivity is defined by:
- the **amount of (different) nodes** (components, subsystems, …) within a system, and
- the **amount of causal connections** between the nodes.

> Possible measurement: the **clustering coefficient**.

### Clustering coefficient (exercise)
- Calculate the **exact** clustering coefficient (no rounding!) for each node and for the whole system.
- A **bidirectional** connection counts as **2** (note: "2! Bidirectional").

## System Dynamics

- **Complex systems cannot be described easily and linearly.**
- **System Dynamics** = the **modelling and simulating of overall systems** to analyse complex and dynamic systems.
- **Variants: Qualitative** and **Quantitative**.

### Qualitative
- **Identification and investigation of feedback loops** between items — *how do they impact each other?*
  - **Reinforcing loops** — positive coupling.
  - **Balancing loops** — negative coupling.
- **Easier to realise** than quantitative.
- Creates a **good overview** of the connections between items.

### Quantitative
- **Modelling and simulating** of the whole system.
- Results are **"real numbers"**.
- Enables the investigation of **many scenarios (runs)**.
- Typically uses **flow charts and process views**.
- Used to identify **non-linear effects**.
- (Software → see *Software Providers*, e.g. **simcision**.)

## Chaos Theory

- **Chaos theory** [a field of research] studies **non-linear dynamic systems**.
- **"Butterfly effect"** — small changes can have a big effect, and **prediction is not possible**.
- Examples: **turbulent flow of gas**, the **internet**.

## Design

> **A design is the process of translating different requirements — with respect to the system purpose — into a (technical) solution.**

**Deliverables of a design (creation):**
- Plan
- Drawings, schematics
- Models
- Software code
- …

- **System Design, integration and production cannot be strictly divided** — they influence each other.
- To create a feasible design, **single parts must be built upfront (prototypes) and tested** (see *Test & Verification*).
- Without knowing **production capabilities**, the result can be **non-producible** (e.g. ball-in-ball) or **not commercially producible** (e.g. all wires would need to be gold).

## System Design Process

Processes within a company can be allocated to one of **3 main classes**:

| Class | Description |
|---|---|
| **Core processes** | Activities where the company works on business with **customers and suppliers**; **value-adding** activities (increasing corporate value, customer value, …). Flow: **customer requirement → core process → customer satisfaction**. |
| **Management processes** | Steer/manage the organisation. |
| **Support processes** | Support the core processes. |

### Core process — example BMW AG (simplified)
| Phase | Meaning |
|---|---|
| **ItO** | **Idea to Offer** |
| **OtO** | **Offer to Order** |
| **OtD** | **Order to Delivery** |
| **DtCC** | **Delivery to Customer Care** |

**ItO — Idea to Offer (simplified):** the core process of development, from the **requirement** through various **ideas and concepts** to **implementation**. At the same time, **purchasing** ensures the procurement of materials, tools, systems, … After successful **testing and validation (verification)** and **industrialisation**, the product can be **released for production**. The aim is to **meet all requirements best** and develop the **optimal product** (customer requirement → ItO → offer → product).

> **System design** is the part of the core process concerned with turning requirements into the technical solution (the ItO development work).

## System Engineering

**System Engineering…**
- is an **interdisciplinary field** of classical engineering and engineering management;
- contains **design, integration, and management of complex systems over their life cycles**;
- is defined in **ISO/IEC 15288** [NM_ISO15288].

### The process / steps of System Engineering
The steps form a loop, surrounded by **Change Management** and **Risk Management**:

1. **Requirement Management** — systematic analysis of the problem and requests from **Customer, Law, Lessons Learned (LeLe)**; break the problem down into requirements; define the requirements of the system.
2. **Ideation / Concept** — search for ideas and solutions (creative process, maybe even **research** instead of development!); define functions and solutions; create the **system architecture**; break down (super)system → subsystem → components; break down requirements into the levels; **interface design**.
3. **Design / Realization** — model creation, simulation and analysis of results; realisation/implementation of functions into real **hardware, E/E, software, …**; integration of the levels; system documentation (function, interfaces, schematics, manual…). → **core engineering work**.
4. **Test & Verification & Validation** — test design; the **"test of the test"** (does the test show the damage mechanism?); test planning; test execution (virtual & hardware) of level tests and integration tests. → **proof by measurement** that every requirement is fulfilled by the system.
5. **Release** — sign-off of the developed system; release to production; take over **accountability** for the working system (according to requirements and law) towards the customer.

Surrounding (continuous) activities:
- **Risk Management** — check if risks can appear to the product, development time/costs, safety, … (e.g. **FMEA**); compare current development with the target → **deviation management**. Risks apply to development, manufacturing process, parts procurement & logistics, technology, …
- **Change Management** — based on changing requirements, the system must be updated; **version control** (system + components). Changing requirements can be caused by **new law, change of mind by customer, LeLe / field issues, …**

> The classic warning image: a system built **without** system design and requirement management ends up like the "tree-swing project" cartoon — each department builds something different from what the customer asked for.

## System Engineering — Challenges

Modern (CPS) projects are harder than classic single-discipline projects:

**Organisational / project challenges**
- Project settings are **more complex** due to increasing **globalization**.
- **Cooperation with many suppliers** / value-chain partners.
- Results must comply with **increasing legal specifications**.
- **Unclear responsibilities and accountabilities** because of unclear boundaries.
- Increasingly **interdisciplinary** approach.
- **Large diversity of interfaces.**
- Increasing **complexity of requirements**.
- Increasing **number of product variants** (more customization).
- **Reduction of product cycle time.**

**Detailed challenges**
- **Interdisciplinary approach** — intelligent systems are interdisciplinary; communication & cooperation across specialists' boundaries are **mandatory**.
- **Diversity of interfaces** — work-sharing of specialised developments is necessary; large number of interfaces → **consistent control of all interfaces is required**.
- **Complexity of requirements** — increasing complexity causes increasing **dynamics** in requirement management.
- **Number of product variants** — increasing customer expectation for individualized products causes more variants → costly **change & variant management** → strengthen **component-kit development** (reusable units).
  - *Fun fact:* a typical passenger car (e.g. VW Golf) has **~425 billion** possible combinations of **wiring harness** because of customization.
- **Reduction of cycle time** — development time is reduced (see VUCA); the **trade-off of quality, cost and time** is hard to find.
- **Distributed sensor network** — many sensors; to describe an object, different data from different (types of) sensors must be combined (**sensor fusion**) although distributed by location (e.g. camera at the windscreen + lidar in the bumper).
- **Handling communication** — systems must intercommunicate (vs former standalone devices) → added complexity (*when* do I get the info? *which* path is prior — internet, Bluetooth, …?).
- **Information gathering** — how to get information out of these systems? A lot of data; system permanently changing; not all data/sub-systems accessible.
- **Hard to verify** — cannot control/"stop" the whole system; who is the root cause (supersystem or system?); too complex to understand each reaction (hard to debug); reaction changes because of an evolving network (e.g. AI).
- **Safety** — is the data from the network trustworthy? New access points of attack (past: only physical/onsite); how to ensure safety if you cannot control the whole network?

> **Accountability discussion (autonomous AI car accident):** possible accountable parties include the car owner (renting company), the customer ("me"), the "driver" (friend), sensor supplier, sensor-fusion developer, car manufacturer, car software/hardware developer, AI software developer, AI trainer, supplier of training datasets, internet supplier, car-to-car/infrastructure interconnection supplier, … → **mastering this complexity is the challenge for the future.**

### System Wheel — why System Engineering is needed
- In the **past**, development was based only on the **realization domains** (mechanics, electronics, …); systems and components were clearly divided (Dept. A = mechanics, Dept. B = electronics).
- With functions **melting into complex mechatronic systems**, **system engineering is needed**. *Example:* a gearbox (mechanic) + electric motor to open the clutch (electric) that confirms via **CAN** (IT).
- With evolving technology, **more disciplines** appear: **AI**, the melting of physical & virtual worlds (cyberspace, web3, VR/AR), and systems becoming more intelligent — **self-diagnostics, self-optimization, self-configuration, self-repair ability**, …

### System Wheel — three perspectives

**Customer perspective (inner ring / "DNA"):**
The customer raises requirements **on system level** (e.g. *"I need an electric motor with 100 kW and 90 % efficiency at 1000 RPM and 25 °C"*). Customer expectations of products:
- **Intelligence** — adaptive, autonomous interaction with the environment; manage **unpredictable** and **dynamic** situations; early recognition of dangerous situations and autonomous strategy.
- **Inter-connection** — communication & cooperation of systems; dynamic networking; geographic closeness unimportant (internet) → global networking; composition into CPS via cloud computing. *But:* global control may be insufficient → **highly dynamic local control required**.
- **Performance increase** — increasing 3-D physical integration of mechanics & electronics (e.g. strip-line printed into the housing instead of separate wires); integration of functions + miniaturization; more automated functions.
- **User-friendly** — adjust to user behaviour. *Past:* the user is the expert and studies manuals; problems = wrong usage. *Future:* the user has no clue and just interacts intuitively; problems are caused by **wrong system design / UI, not the user**.

**Properties perspective (middle ring):**
- The **property engineer** translates customer requirements into **system properties** for their specific property — the **"voice of the customer"** for that property.
- Goal: **overarching property optimization** based on the **technical solution kits** from the component-teams — **not** a single-component optimum.
- Decides the technical solution (e.g. reach the acoustic target via a **better bearing** or **extra sound insulation**) and breaks "solution-open requirements" down to component-teams (e.g. set **98 %** for power electronics, **97 %** for the motor, **95 %** for the gearbox).
- Must **think in system functions** (what should the system do), not in components or company org-structures.

**Product perspective (outer / integrating view):**
- The **project leader / system engineer mediates** between property engineers and takes care of process compliance.
- Because properties in systems are **connected and impact each other**, the system engineer must **decide in case of conflicting targets**.
- *Conflict example:* adding **sound insulation** reaches the acoustic property but **mismatches weight** (and thus efficiency); **active noise cancellation** is less effective acoustically and more cost-sensitive but reaches weight & efficiency.

**Realization domain (the engineering disciplines):**
- Offers a **decision matrix** of possible solutions and the **kit of components** from the component-teams.
- Designs the technical solutions of the decided component. *Example kit:* a **SiC inverter** with 98 % efficiency, a **3-level inverter** with 97 %, or a **high-voltage inverter** with 99 %.

## MBSE, MDSD & Digital Engineering

### MBSE — Model-Based Systems Engineering
- Like the **System Wheel** but **extended with a model** — not only text description, but **modelling the system**.
- Enables **communication between engineers from different disciplines** (mechanics, electronics, SW, …).
- Contains **all relevant comprehensive system information**, described **independently of single realization domains**.
- Needs a **harmonized, synchronized modelling language (code)** → supported by software.
- The successor of MBSE, **"Digital Engineering"**, is in development.

**MBSE benefits:**
- Better **visualization**.
- Creation of **architectures and dependencies** → increased **traceability**.
- **Automated tests and plausibility checks**.
- **Different views** of the same system (e.g. packaging specialist sees impacts on component sizes; E/E specialist sees impacts on energy consumption).
- Interconnections are **known and documented** → changes can be foreseen (e.g. how an e-motor housing's packaging affects the electronics inside: longer wires = less efficiency, EMC impact, weight, …).
- **Direct software creation** out of the model (see MDSD).

**Modelling languages:** **UML** (Unified Modeling Language) and **SysML** (Systems Modeling Language).

### MDSD — Model-Driven Software Development (a.k.a. MDD)
Used to **automatically create**, directly out of the model **without any coding**:
- **Functional software**
- **Tests**
- **Documentation**

*Example:* **Matlab Simulink** → C-code created directly from the Simulink model.

| Advantages | Disadvantages |
|---|---|
| Higher level of **abstraction** than pure coding → better understandable | **More effort** for the initial creation of the modelling |
| **Increased development speed** | Not all functions can be created from the model → integrating **manual code** afterwards is tricky |
| Faster creation of **test cases** that fit the system requirement (not just single components) | **Troubleshooting** at system level is harder because of the manually added code |

### Digital Engineering
- **INCOSE** (International Council on Systems Engineering) and, in Germany, **GfSE** (Gesellschaft für Systems Engineering) define methods to develop systems.
- Digital Engineering uses the power of **"digital twins"** of the system, to see performance **live** and even **interact virtually** with the real system.
- Uses: **MBSE · AI · CAD/CAE · Additive manufacturing · VR/AR**, …

## Summary

- Caused by the increasing **complexity** of components, environment (**VUCA**) and their interconnections, engineers must develop **whole systems and system functions**, not just single sub-components.
- The discipline of **system engineering and system development** enables the organisation to deal with these complexities.
- **Holistic thinking** in system design **avoids failures** and drives the product to its **overall optimum** instead of a singular solution.
